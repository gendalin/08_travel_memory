### Fix 1 — A day-bound must-visit loses its day (P0 · Effort S)
Problem: "Must visit Nezu Museum on Day 4." with Nezu closed on Day 4 produces no Conflict; Nezu is scheduled on Day 2 on both the create path and the State-edit path, and the plan reports itself valid.
Evidence: H5 `tag = {kind:"must_visit", placeId:"nezu_museum"}` (no day); edit outcome `proposal`, Nezu on Day 2; create path `valid: true`, Nezu on Day 2. Control (Nezu closed every trip day) does return a Conflict, so the conflict machinery works; the day is lost before it.
Likely root cause: `placePhrase()` in `src/application/decompose/tagConsidering.ts` strips "on Day N" to isolate the place name, and the `must_visit` tag type has no `dayIndex`. `dayIndexIn(text)` is computed at the top of `tagConsidering` and then not used for this branch. The validator's `must_visit_missing` checks presence only.
Recommended change: add optional `dayIndex` to the `must_visit` tag and set it from `dayIndexIn`; in `generateFirstPlan` and `adaptPlanToState` only offer that day's roles to a day-bound pin; add validator code `must_visit_wrong_day`; when the place is closed that weekday, return a Conflict naming place, day and weekday.
Expected impact: removes the only constraint-violation path found; H5 6 → 9–10; `constraint violation` invariant → PASS.
Validation scenario: H5 (all three paths).

### Fix 2 — A State change is not always a Reframe and can commit without preview (P0 · SPEC_CONFLICT · Effort S, plus a product decision)
Problem: adding "Day 2 dinner: ramen" to State commits immediately as type `replace`; adding a must-visit is typed `reorganize`. The eval spec says any State change is a Reframe and is previewed before commit.
Evidence: H4 probe `{outcome:"commit_replace", type:"replace", stateChanged:true, previewRequired:false}`; H5 edit path `type: "reorganize"` with a non-empty stateDiff.
Likely root cause: `classifyChange()` (`src/domain/proposals/classify.ts`) returns early on the plan diff and reads `stateDiff` only when the plan diff is empty. The immediate commit is intentional — `product_spec.md` §7.6 (revised 2026-09-29) says "Replace: commit immediately (one stop, nothing else moved)".
Recommended change: (a) regardless of the decision below, return `reframe` whenever `stateDiff` is non-empty, so Receipts and the classifier are truthful; (b) decide which spec wins for the single-swap fast path. If the product keeps it, amend eval spec §11–12 to allow "one in-place swap caused by a State edit may commit immediately" and keep the probe as a regression guard; if the eval spec wins, route `commit_replace` through the normal preview.
Expected impact: `atomic Reframe` invariant → PASS; H4 6 → 10.
Validation scenario: H4 (probe), H5 (edit-path type).

Expected impact: M3 5 → 9; closes the Memory-lifecycle gap (§8).

Problem: with the bundled pace memory (3 stops a day), a bookstore memory changes zero stops. The same holds for the bundled grocery and discount-variety memories.

Likely root cause: `rolesForPace(3)` keeps only the required roles `main_destination`, `lunch` and `dinner`. `main_destination` admits museums, temples, parks and similar, but not bookstores or shops, and extension roles appear only at 4 or more stops.
Recommended change: let an active interest preference widen the category gate of `main_destination`, within `claimsAllowed`. Alternatively, at pace 3 or below, let one required slot be "an interest the traveller keeps returning to".
Expected impact: Memory visibly shapes the demo traveller's own plan; this is the core Memory → recommendation promise. M1 relevance 1 → 2.
Validation scenario: M1 (paced variant).

### Fix 6 — The Memory claim bound is bypassed by ranking, and the rationale misstates provenance (P1 · Effort S)
Problem: a memory allowed 2 claims places 4 bookstores. The reason on each says "Bookstore turns up 1 times in your photos and saved places." for a memory that came from an explicit statement.
Evidence: M1 `claim_bound {bookstoresInPlan: 4, claimLimit: 2}`, `provenance_truthful` failed; R2 4 bookstores (`bookstore_cap`).
Likely root cause: `claimsAllowed` gates only the first-claim loop in `generateFirstPlan`, while `scorePlace()` keeps the full `memoryMatch` after the claims are spent. The reason template in `explainStop.ts` assumes photo/saved-place evidence, which is also why it prints "1 times".
Recommended change: once a memory reaches its claim limit, decay its `memoryMatch` (for example ×0.25) for the rest of the trip. Build the reason from `provenanceLabel(memory.provenance.type)` and pluralise the count.
Expected impact: no memory dominates; rationale matches evidence. M1 efficiency and explainability → 2; R2 → 10.
Validation scenario: M1, R2.

### Fix 7 — Discovery is anchored to the lodging and has no area stage (P1 · Effort M–L)
Problem: a Showa / literary / kissaten intent never reaches Jimbocho, Shimokitazawa, Koenji or Yanaka. 37 of 104 pool places are in Kuramae, and only 1 of 12 Intent terms ("kissaten") reaches any search query.
Evidence: R1 `expectedAreaHits: []`, `stateTermsLost` has 11 of 12 terms; `area_candidates.stageExists: false`. R2: 56% of stops are in Kuramae.
Likely root cause: `defaultTextQuery` is `<lodging> <category>`. The query planner may only reword categories the profile already asked for, and retrieval is centred on the lodging.
Recommended change: add an area stage before POI retrieval. Intent terms go through a small code-owned area table (e.g. jimbocho: used books, kissaten; koenji: vintage, live music; yanaka: Showa streets), so the model can choose areas but cannot invent them. Issue `<area> <category>` searches for the top 1–2 areas within transit reach, alongside the lodging searches. Record the area choice in the trace. This widens retrieval per trip; it does not grow the bundled fixture (the 80–150 target stays cancelled).
Expected impact: candidate recall proxy 1 → 2; more distinctive plans for intent-led trips. Costs a few extra Places calls per live trip.
Validation scenario: R1 (and R2 area saturation).

### Fix 8 — A "slow" Intent does not change how full the day is (P1 · Effort S)
Problem: "slow neighborhood exploration" and "Explore Tokyo slowly" still produce 5 stops a day, with a bar every night.
Evidence: R1 `stopsPerDay [5,5,5,5,5]`, `nightcaps: 5`; M1 has the same shape.
Likely root cause: pace comes only from a `pattern` memory or `DEFAULT_STOPS_PER_DAY = 5`. Intent text feeds `stateMatch` only, and `toTerms` cannot map "slowly" to pace.
Recommended change: Stage B decomposition maps pace words to a structured Considering tag (`pace: 3–4 stops`), shown and editable in State. It follows the lattice: State > pattern memory > default.
Expected impact: plans match the stated tempo; the nightly bar goes unless asked for.
Validation scenario: R1 `slow_pace`, M1.

### Fix 9 — Reframe and Reorganize choose what to drop by position (P1 · Effort S)
Problem: "I feel tired. Fewer spots." removes dinner, a required role, on all 5 days. Rain after 3 pm removes an indoor yakiniku dinner.
Evidence: H3 removed = 5 × dinner, `daysTouched 5/5`; H2 dropped "Yakiniku Yoin Ebisu [dinner]".
Likely root cause: `reduceStopsPerDay` drops the last stop of each day; `compressDayBefore` treats weather as an end-of-day cut-off for every stop, indoor or not.
Recommended change: drop the lowest-value optional or non-meal stop first and never a required meal role. When the trigger is momentary ("I feel tired"), propose today / the next day, or ask. For rain, re-plan only outdoor categories after the cut-off (park, viewpoint, market, outdoor temple grounds).
Expected impact: smaller, more sensible proposals; H2 → 9, H3 → 10.
Validation scenario: H2, H3.

### Fix 10 — A Conflict gives no concrete reason or structured options (P1 · Effort S)
Problem: Conflicts carry only `{message, consideringId}`. The spec requires move-day / remove / edit options.
Evidence: H5 `resolution_options` failed; the control Conflict says "couldn't fit it into any day" without naming the closed days.
Recommended change: add `options: [{kind:'move_day', dayIndex}…, {kind:'remove'}, {kind:'edit'}]`, computed by code from the days the place is open, and name the blocking reason ("closed on Thursdays").
Expected impact: H5 explainability → 2.
Validation scenario: H5.

### Fix 11 — An overridden Memory disappears from the explanation (P1 · Effort S)
Problem: when State wins over a conflicting Memory, the stop's reasons never say so.
Evidence: M2 Senso-ji reasons cite only the Intent; nothing mentions the aversion it overrode.
Recommended change: when a placed stop has negative `memoryMatch` and a stated reason, add a secondary reason, for example "You usually prefer quieter places — included because this trip you asked for landmarks." Record it as a `PlanTension` with `because: 'state_override'`.
Expected impact: M2 explainability → 2; the spec's State > Memory rule becomes visible to the user.
Validation scenario: M2.

## 10. Strengthening Opportunities

These are not bugs but high-value improvements.

1. **Memory conflict weighting as a first-class record.** Extend `PlanTension` beyond budget to "State overrode Memory" and "Memory claim exhausted". Every trade-off the lattice makes then lands in the trace and the Receipt, not only in scores.
2. **A product-native recommendation trace.** `generateFirstPlan` returns the stages this eval reconstructs (signals → expansion → areas → pool → filters → scores → diversity → route) as data. The eval would then audit the planner's own record instead of re-deriving it, and "Why this day" could read from the same source.
3. **Proposal scope inference.** Before building a candidate, classify each chat trigger's temporal scope (this stop / today / rest of trip) and ask when it is ambiguous. This would have made H3 minimal by construction and prevents the same over-reach on future triggers.
